# admin/

챗봇 답변을 UI로 관리하는 도구.

```bash
export AWS_PROFILE=hhr-chatbot
export CONTENT_BUCKET=hhr-chatbot-content
export LEX_BOT_ID=QFUOZQHBTO

aws s3 cp s3://$CONTENT_BUCKET/content/current.json content/current.json   # 최신 받기
yarn admin                                                                 # http://127.0.0.1:5174
```

## 왜 로컬에서 도나요

혼자 쓰는 도구라 **의도적으로 로컬 전용**입니다.

호스팅하면 Cognito(인증) + Admin Lambda + API Gateway + 별도 CloudFront가 필요하고,
관리 화면이 인터넷에 노출되는 것 자체가 새로운 공격면이 됩니다.
로컬 바인딩(`127.0.0.1`)이면 인증이 필요 없고, AWS 리소스도 늘지 않고, 비용도 0입니다.

나중에 호스팅이 필요해지면 `vite.admin.config.ts`의 `adminApi()` 핸들러를
그대로 Lambda로 옮기면 됩니다. 그래서 API 경계를 미리 분리해뒀습니다.

## 화면

```
┌──────────────────────────────────────────────────────────────────┐
│ 저장 │ 발행(즉시) │ Lex 발행 │ UI 반영            ← 상태/오류 표시 │
├───────────────┬──────────────────────────┬───────────────────────┤
│ 엔트리 목록    │  블록 에디터              │  미리보기              │
│ 미응답 질문    │  ko / en 탭              │  (실제 챗봇 컴포넌트)   │
└───────────────┴──────────────────────────┴───────────────────────┘
```

**미리보기는 챗봇이 쓰는 `BlockRenderer`를 그대로 씁니다.** 따로 만들지 않으므로
"어드민에선 멀쩡한데 실제로는 깨지는" 상황이 구조적으로 생기지 않습니다.

## 버튼 4개의 차이

| 버튼 | 하는 일 | 언제 |
|---|---|---|
| **저장** | `content/current.json`에 기록 | 편집 직후 (로컬) |
| **발행 (즉시)** | S3 업로드 → 챗봇에 반영 | 답변을 고쳤을 때. Lex는 안 건드림 |
| **Lex 발행** | 발화만 담은 zip → import → build | **발화를 고쳤을 때만.** 2~3분 |
| **UI 반영** | 인사말/홈/fallback을 프론트 번들에 주입 | 화면 문구를 고쳤을 때 (프론트 재배포 필요) |

## 검증

저장 전에 자동으로 확인하고, 오류가 있으면 발행 버튼이 잠깁니다.

- 버튼이 **등록되지 않은 발화**를 가리키는 경우 ← 실제로 프로덕션에 있던 버그
  (Lex 퍼지 매칭 덕에 겉보기엔 동작해서 눈치채기 어려웠음)
- 발화 중복 (두 인텐트가 같은 발화를 가짐)
- 잘못된 이미지/링크 URL, 라벨 없는 버튼
- 발화는 있는데 답변이 빈 로케일

## 미응답 질문 인박스

CloudWatch에서 `hit:false` 로그를 모아 빈도순으로 보여줍니다.
= **사람들이 물어봤는데 답을 못 한 질문 목록**.

자주 나오는 게 있으면 해당 발화를 인텐트에 추가하고 `Lex 발행`을 누르면 됩니다.
이 루프가 챗봇을 실제 질문에 맞춰 성장시킵니다.
